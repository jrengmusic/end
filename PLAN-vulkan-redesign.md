## Context

END's Vulkan backend (`jam::vulkan::LowLevelGraphicsContext`/`Graphics`) works (Sprints 50-54) but has 6 grounded defects and a per-draw-immediate architecture that caps it at JUCE's design ceiling:

1. **Clip-state desync** — `isStencilClipActive`/`currentStencilRef` (`jam_VulkanLowLevelGraphicsContext.h:750,753`) sit outside the saved `State` struct (`:708-727`); `saveState()`/`restoreState()` never touch them, so a clip inside a save/restore block leaks stencil-gating onto every subsequent draw for the rest of the frame. **Confirmed live** — ARCHITECT's own report this session: "clipToImageAlpha breaks path rendering."
2. **Path fill winding bug** — `triangulatePath` earcuts each sub-path independently (`jam_VulkanLowLevelGraphicsContextPath.cpp:53,82-83`); a holed/self-intersecting path fills the hole solid, ignoring JUCE's winding rule.
3. **Nested clip intersection wrong** — `stencilWriteState` (`jam_VulkanPipelinesState.cpp:232-243`, `passOp` at `:236`) uses `passOp=REPLACE, compareOp=ALWAYS` — an inner clip's write isn't gated by the outer, so multi-level path/image-alpha clips don't truly intersect.
4. **Stencil shared across transparency layers** — `TransparencyTarget` (`jam_VulkanTransparencyStack.h:26-31`) owns only a color attachment; the stencil view is caller-supplied and shared across all nesting levels, never cleared per-layer.
5. **No anti-aliasing** — every `multisampleState()` call is hardcoded `VK_SAMPLE_COUNT_1_BIT` (`jam_VulkanPipelinesState.cpp:203-210`).
6. **Image descriptor churn + hard cap** — `allocateImageDescriptor` (`jam_VulkanGraphics.cpp:317-347`) allocates a fresh `VkDescriptorSet` per `drawImage` call from a pool capped at `maxImageSamplerDescriptors{64}`.

This plan redesigns the engine downstream of JUCE's `Graphics` API (zero surface change) to fix all 6 defects and add: unified vertex-pulling SSBO for all quad primitives, bindless image descriptors, clip-as-data, 4x MSAA with capability+performance calibration, refresh-rate-aware frame budgeting, and a full Shadertoy-parity multi-pass post-process pipeline (END-owned, shaderc-driven). Outcome: correct, deterministic clipping/winding/layering, AA'd output, and a shader/post-process ceiling JUCE cannot reach natively — while JUCE's native/software fallback path stays fully intact.

7. (e) post-process shader tick rate stays independently `juce::Timer`-driven (existing pattern, `Processor.cpp:114-120`) — decoupled from the core engine's fixed-Hz capability requirement.
8. `(c)` draw-indirect excluded — `vkCmdDrawIndirectCount` is a MoltenVK no-op; plain indirect is CPU-looped. Zero GPU offload on target platform.
9. Draw order stays JUCE-immediate (no whole-frame batching/regroup) — SSBO records are appended in paint order, one draw-range per paint op.

**Design notes (not new names, technical grounding):**
- Even-odd/nonzero winding share ONE accumulate pass (`INCR_WRAP`/`DECR_WRAP`, full byte, `compareOp ALWAYS` since the scratch buffer is freshly cleared every call — no relation to the forbidden bit-partition, since nothing else ever writes this scratch byte). The cover draw selects nonzero vs. even-odd purely via `vkCmdSetStencilCompareMask` (`0xFF` vs `0x01`) — arithmetic wraparound mod 256 is even, so the accumulated byte's LSB always equals true winding parity regardless of sign/wraparound. No `INVERT`, no second pass.
- Composite-back: accumulate + cover render in the SAME scratch render pass/subpass (fixed-function write-then-test ordering within one pass, the same guarantee `clipToPath` already relies on); the resulting scratch COLOR image (not stencil) is then composited onto the resumed main pass via the EXISTING `transformedImage`/`transformedImageStencil` pipeline as a textured quad — mirrors the established transparency-composite pattern, never touches the main stencil attachment.
- `TRIANGLE_FAN` avoided (MoltenVK/Metal has no native fan primitive — flagged as reasoning, not locally re-verified against vendored SDK); CPU-side fan-to-`TRIANGLE_LIST` expansion used instead, reusing the existing indexed-draw path.
- No new shader compilation needed — `StagePair::windingStencil`/`windingCover` reuse already-baked `fill_rect.vert/.frag`/`fill_rect_alpha.frag`/`instanced.vert` bytecode under new stage-pair slots, mirroring Step A2's `path`/`pathAlpha` reuse-under-new-slot precedent exactly.

**Flagged, not fixed this step (pre-existing architectural gap, same shape as existing code, out of Step A6's scope):** `Graphics::endRenderPass()`/`beginRenderPassLoad()` always resume the MAIN swapchain framebuffer — if a complex `fillPath()` (or an uncached texture upload) runs while nested inside an active `beginTransparencyLayer`, the interrupted offscreen transparency pass gets incorrectly resumed onto the main swapchain instead of back into the transparency target. This exact shape already existed for texture uploads (`ensureImageTextureUploaded`) before this step; Step A6's scratch-target code follows the same established (flawed) pattern rather than diverging. A proper fix requires `Graphics` to track a resumable-render-target stack across 3+ call sites — out of this sprint's step scope, flagged for ARCHITECT disposition (future debt, not silently fixed, not silently ignored).

### Step A3: Bindless image descriptor path

**Scope:** `jam_vulkan/context/jam_VulkanGraphics.{h,cpp}`, `jam_VulkanGraphicsSetup.cpp`, `jam_vulkan/resource/jam_VulkanTextureCache.{h,cpp}`
**Action:** **No dual path. No fallback. No legacy per-draw descriptor allocation coexisting with bindless.** `allocateImageDescriptor`'s per-draw combined-image-sampler mechanism (`jam_VulkanGraphics.cpp:317-347`) is DELETED outright, not kept as a conditional branch. ### Step A6: Non-zero/even-odd winding stencil-then-cover (defect #2)

**Corrected design (this session, ARCHITECT-approved) — supersedes the original bit-partition idea below.** Vulkan stencil ops compute their result from the FULL 8-bit stored value before `writeMask` filters which bits get merged back — `writeMask` does not scope the OP's computation itself. This means a bit-partition scheme (low bits = clip depth, high bit = winding scratch) is unsound: an `INCR_WRAP` meant to toggle one bit actually computes `(fullByte + 1)` first, and whether the target bit flips depends on carry-out from whatever the OTHER mechanism's bits currently hold. Given Step A5's clip depth occupies the full byte as an exact, persistent, monotonic counter, no bit range is safely available for a concurrent winding-scratch use.

**Fix: isolated scratch stencil target.** The winding accumulate/cover passes render into their OWN scratch depth/stencil image (sized to the path's device-space bounding box, allocated/reused per complex `fillPath` call), completely decoupled from the main stencil attachment that carries clip depth. Sequence per complex-path `fillPath` call:
1. Begin a small offscreen render pass targeting the scratch stencil image (fresh `LOAD_OP_CLEAR` to 0 every call — no cross-call state, no interaction with clip depth whatsoever).
2. `windingStencilAccumulate` — per-subpath triangle fan (NOT full earcut — correctness comes from stencil parity, not triangulation) into the scratch target: `INCR_WRAP` (front-facing) / `DECR_WRAP` (back-facing), `colorWriteMask=0`.
3. `windingCoverOpaque`/`windingCoverAlpha` — within the SAME scratch pass or a second pass reading the scratch stencil: draws the path's bbox quad, tests the scratch value (`compareOp NOT_EQUAL, reference=0` for `juce::Path::isUsingNonZeroWinding()==true`; even-odd needs a distinct encoding — Engineer to determine the correct Vulkan-representable approach, e.g. two calls with alternating compare, since a bitmask parity trick has the same full-byte-computation problem noted above and must not be reintroduced) — writes color to the MAIN swapchain/scene target (not the scratch image).
4. Scratch stencil image is discarded/reset next call — it never touches the main stencil attachment or clip-depth bits.

**Scope:** `jam_VulkanLowLevelGraphicsContextPath.cpp` (`triangulatePath`, `fillPath`), `jam_VulkanPipelines.{h,cpp}` (new pipelines from Names Gate), new scratch stencil target (name pending Names Gate — propose during implementation, mirroring `TransparencyTarget`'s owned-`Image`-per-target RAII pattern).
**Action:** `fillPath` branches on path complexity (read via `juce::Path::Iterator`, count subpaths + detect self-intersection eligibility): a single simple convex subpath keeps the existing fast fan/earcut path unchanged (cheap case preserved). A complex/holed path uses the isolated scratch-target sequence above.
**Validation:** Auditor constructs a holed-path test case (e.g. a ring shape) and confirms the hole renders unfilled (not solid) — direct regression test for defect #2. ### Step A8: Per-transparency-layer stencil isolation (defect #4)

**Scope:** `jam_vulkan/resource/jam_VulkanTransparencyStack.{h,cpp}`, `jam_vulkan/context/jam_VulkanLowLevelGraphicsContextTransparency.cpp`

**Blocking Vulkan constraint found + resolved (this session, ARCHITECT-approved):** `vkCmdCopyImage` is a transfer command, illegal inside an active render-pass instance — it cannot run between the pass's `LOAD_OP_CLEAR` and the first content draw within one `vkCmdBeginRenderPass`/`vkCmdEndRenderPass` pair. Neither existing render-pass object supports the needed shape (clear color unconditionally + load/preserve stencil conditionally) in one instance: the CLEAR-variant `renderPass` clears both attachments unconditionally (load ops are fixed per-`VkRenderPass`-object, not switchable per `vkCmdBeginRenderPass` call); the LOAD-variant `renderPassLoad` loads both, which would incorrectly preserve stale color from the layer's previous use.

**Fix, locked:** reuse `renderPassLoad` for this invocation (proven framebuffer-compatible with the same `target.framebuffer` — Vulkan render-pass compatibility depends only on matching attachment format/sample-count, not load/store ops; this exact cross-object reuse is already an established pattern in this codebase, `sceneFramebuffer` is built against `renderPass` but used with `renderPassLoad` in `beginRenderPassLoad()`). Sequence, entirely OUTSIDE any active render-pass instance, before `vkCmdBeginRenderPass`:
1. `vkCmdClearColorImage` the layer's color image to transparent black (a legal transfer op outside a render pass — replaces the render-pass-level `LOAD_OP_CLEAR` this invocation intentionally skips by using `renderPassLoad`).
2. If `currentState.stencilClipDepth > 0`: `vkCmdCopyImage` the outer clip's mask from `Graphics::stencilImage` into the layer's own stencil image (`VK_IMAGE_ASPECT_STENCIL_BIT`, full image or scoped to `currentState.deviceSpaceClipList.getBounds()` — Engineer's choice, both correct, full-image copy is simpler and equally correct since bits outside the clip region won't match any content record's baked `stencilRef` regardless of their value). Correct layout transitions required: `Graphics::stencilImage` → `TRANSFER_SRC_OPTIMAL` before copy, back to `DEPTH_STENCIL_ATTACHMENT_OPTIMAL` after; layer's `stencil` → `TRANSFER_DST_OPTIMAL` before copy, then `DEPTH_STENCIL_ATTACHMENT_OPTIMAL` before the render pass begins. If `stencilClipDepth == 0`: skip the copy — the layer's stencil needs no content beyond whatever `vkCmdClearDepthStencilImage` (paired with the color clear above) established, so also add an explicit stencil clear-to-zero in this branch (since `renderPassLoad` no longer clears it via the render pass itself).
3. Handle `target.stencil`'s first-ever-use layout: starts `VK_IMAGE_LAYOUT_UNDEFINED` until first transitioned — the sequence above's own transition-before-copy-or-clear covers this (transition FROM whatever the actual current layout is, tracked per the image's own lifecycle, not assumed).
4. New `Graphics::getRenderPassLoad()` public accessor (Names Gate — verb/noun matching `getRenderPass()`'s existing convention) to make `renderPassLoad` available to this call site.
Then `vkCmdBeginRenderPass` with `renderPassLoad` (LOAD both attachments — color already cleared manually in step 1, stencil already cleared-or-clip-copied in step 2/the else-branch).

YAGNI: no LRU eviction added for bindless textures (not yet needed), no full sampler array (single `linearSampler` suffices), no per-frame adaptive MSAA (session-locked instead). `jam_VulkanLowLevelGraphicsContext.h` (already 769 lines) — Engineer splits further if the record/clip logic pushes it past 300 (per-file, doc-excluded).
- **E (Explicit):** Clip carried as visible per-primitive data (`PrimitiveRecord::clip`/`stencilRef`) — no hidden out-of-band state (directly retires the two members that violated this). Winding rule read from `juce::Path::isUsingNonZeroWinding()`, never inferred. `targetFrameBudgetMs` crosses the JAM/END boundary as an explicit parameter, not a global.
- **S (SSOT):** One `PrimitiveRecord` layout for all quad primitives. `activeSampleCount` read from one member by every pipeline's `multisampleState()`. `postProcessBufferScale` computed in one place. Bindless index computed once per texture upload, not per draw.
- **S (Stateless):** `isStencilClipActive`/`currentStencilRef` (persistent, out-of-band, machinery-tracked) removed — replaced by `currentState.stencilClipDepth`, which is Model-analogous state properly scoped to `State`'s save/restore lifecycle, not orchestrator-tracked machinery state.

- **D (Deterministic):** Clip desync eliminated by construction (A4). Winding/nesting made correct (A5/A6) — same input path always produces the same fill. MSAA locked-for-session (A7) — same paint stream on the same machine always renders the same AA level after calibration, never mid-session flapping.

## Phase C — Canonical glyph pipeline: GlyphAtlas relocation + revived fast CPU path + dual-engine text rendering

**ARCHITECT-approved, this session (2026-07-01), via plan mode.**

**Context:** JUCE's own glyph rendering is too slow for END's terminal throughput needs (ARCHITECT's own prior measurement: a previous fast CPU/SIMD glyph pipeline in this codebase matched GPU throughput on a real running terminal). That pipeline (`glyph::Arrangement`/`glyph::Atlas::Packer`/`glyph::LRUCache`/`glyph::Graphics`/`glyph::Constraint`/`glyph::Atlas::Box`, ~7,000 lines, mature — survived 5 prior refactors) was deleted in commit `1bd4b3593` ("JAM: Vulkan LLGC infrastructure") with a commit message claiming "fonts/ moved from jam_graphics → jam_vulkan" that never actually completed: the current `jam::GlyphAtlas` (`jam_graphics/fonts/`) is a smaller, simpler LRU-based rewrite, and `jam::vulkan::TextureCache` independently grew its own separate GPU-mirror atlas storage. Goal: make `jam::GlyphAtlas` the single canonical text-rendering path for BOTH the Vulkan engine and a CPU fallback (when Vulkan is unavailable/disabled) — completing the original relocation intent, reviving the fast CPU pipeline, and ensuring JUCE's own native renderers (CoreGraphics/Direct2D/software) never run for text (or anything) in this app again.

**Key facts grounding this phase (gathered this session, verified against real code/headers, not assumed):**
- `jam_graphics` (current `GlyphAtlas` home) declares zero dependency on `jam_vulkan`; `jam_vulkan` depends on `jam_graphics` — the dependency arrow only points one way. `GlyphAtlas` cannot hold a `VkImage` while it stays in `jam_graphics` without inverting that arrow into a circular module dependency.
- `jam::vulkan::Registry::createContext` is already assigned to `juce::ComponentPeer::externalContextFactory` (`jam_VulkanRegistry.h:41`) — the *only* cross-platform hook that intercepts JUCE's rendering regardless of engine, confirmed invoked before any engine branching on macOS (`juce_NSViewComponentPeer_mac.mm:1033`) and Windows (`juce_Windowing_windows.cpp:2459`).
- JUCE's actual DEFAULT non-Vulkan renderer is **not** `LowLevelGraphicsSoftwareRenderer` — it's `CoreGraphicsContext` (mac, hardcoded stack object inside JUCE's own `renderRect()`, not injectable) and `Direct2DGraphicsContext` (Windows, file-local classes, not injectable). `LookAndFeel::createGraphicsContext()` (which returns `LowLevelGraphicsSoftwareRenderer`) is only reached in JUCE's own already-degraded fallback (software explicitly forced, or Wine) — it does **not** intercept the real default accelerated path on mac/Windows. Confirmed via direct JUCE source read this session.
- Consequence: achieving "fast glyph rendering for ALL JUCE text rendering, whatever the engine" requires `externalContextFactory` to **never return nullptr** — always either the Vulkan LLGC or a new custom CPU LLGC. Returning any non-null context means JUCE performs **zero** presentation of its own (confirmed: mac returns immediately after `handlePaint`, never touches the OS-supplied `CGContextRef` again; Windows never blits `ps.hdc`) — our CPU LLGC must present itself.
- `juce::LowLevelGraphicsContext::drawGlyphs` signature (current JUCE, confirmed via source): `virtual void drawGlyphs (Span<const uint16_t>, Span<const Point<float>>, const AffineTransform&) = 0;` — a batched call, not per-glyph. `LowLevelGraphicsSoftwareRenderer` is public, non-`final`, constructible from an owned `Image`, and implements every other virtual — a subclass overriding only `drawGlyphs` inherits full working behavior for everything else.

### Step C1: Relocate `GlyphAtlas` into the `jam_vulkan` module (namespace stays bare `jam::`, deliberate — ARCHITECT-confirmed: neither the atlas nor the new CPU renderer are Vulkan concepts, even though both physically live in the `jam_vulkan` module for build/dependency reasons)

**Scope:** Move `jam_graphics/fonts/jam_GlyphAtlas.h/.cpp` → `jam_vulkan/font/jam_GlyphAtlas.h/.cpp` (namespace unchanged: `jam::GlyphAtlas`, NOT `jam::vulkan::GlyphAtlas`). Update `jam_graphics.h`/`jam_vulkan.h` module declarations and every include/call site (`TextureCache`, `LowLevelGraphicsContextGlyph.cpp`, `Registry.h`).
**Action:** `GlyphAtlas` gains direct ownership of its GPU-side mirror — absorbs `TextureCache::atlasImages`/`atlasBindlessIndex`/`ensureGlyphAtlas`/`uploadGlyphAtlasImage`/`getAtlasVkImage`/`getAtlasView`/`createAtlasImage` wholesale (these currently live in `TextureCache` only because the atlas couldn't legally own a `VkImage` before this move). `TextureCache` shrinks to purely the generic per-image cache (rename `CachedTexture`→`Entry`, `width`/`height`→`jam::Size<int>` — both already-agreed fixes from this session's audit, executed here since this is the natural point of contact).
**Validation:** Auditor confirms zero remaining atlas-specific members/methods in `TextureCache`; confirms `GlyphAtlas`'s CPU-side surface (shaping/packing/rasterization) has zero direct Vulkan API calls in its own logic — only the upload/GPU-mirror methods touch `VkImage`/`Device` (clean internal seam, preserving reusability for the CPU-only path in Step C4/C5).

### Step C2: Restore per-window atlas bindless-slot bookkeeping (corrected mid-execution — original "shared BindlessAllocator counter" premise was wrong, superseded here)

**Root cause (found during C2 design, confirmed by ARCHITECT):** Step C1's Auditor pass (F3) flagged that the atlas's bindless-slot bookkeeping (`gpuBindlessIndex`, a `Type→slot number` map) landed on the shared, Registry-wide `GlyphAtlas` — but a bindless array **slot number** is not a property of the atlas at all. Each window (`Graphics` instance) owns its own independent `VkDescriptorSet` (set 1) with its own array — two windows sampling the SAME shared atlas `VkImage` can legitimately have it bound at two DIFFERENT slot numbers in their own separate arrays (window A's array may already hold 3 other textures, landing the atlas at slot 3; window B's empty array lands it at slot 0). Storing "the" slot globally on the shared atlas breaks every window after the first. This is not hypothetical — ARCHITECT confirmed END will have popup windows (multiple native OS windows are planned, real, near-term). The original Step C2 premise (a shared bindless-index *counter*) was itself based on a misreading — the counter (`TextureCache::nextBindlessTextureIndex`) was already correctly per-window all along; nothing about it needed sharing or extracting.

**Scope:** `jam_vulkan/font/jam_GlyphAtlas.h/.cpp` (remove), `jam_vulkan/resource/jam_VulkanTextureCache.h/.cpp` (restore, correctly scoped), `jam_vulkan/context/jam_VulkanGraphics.cpp` (`ensureGlyphAtlas`).
**Action:**
1. Remove `gpuBindlessIndex`/`getAtlasBindlessIndex(Type)`/`setAtlasBindlessIndex(Type,int)` from `GlyphAtlas` entirely — the shared atlas keeps only the actual GPU image/view handles (`gpuImages`, correctly Registry-wide), never per-window slot bookkeeping.
2. Restore a `HashMap<jam::GlyphAtlas::Type, int> atlasBindlessIndex` member on `TextureCache` (per-window — mirrors its pre-Step-C1 shape, just no longer bundled with the atlas's own GPU images) with matching `getAtlasBindlessIndex(Type)`/`setAtlasBindlessIndex(Type,int)` accessors.
3. `Graphics::ensureGlyphAtlas` checks/assigns/writes against `textureCache.getAtlasBindlessIndex(type)`/`setAtlasBindlessIndex(...)` instead of `atlas.getAtlasBindlessIndex`/`atlas.setAtlasBindlessIndex` — each window now independently tracks its own slot assignment for the shared atlas image, exactly like it already does for `sceneColorBindlessIndex`/`TransparencyTarget::bindlessIndex`.
**Validation:** Auditor confirms zero remaining bindless-slot bookkeeping on `GlyphAtlas` (only GPU image/view handles remain). Constructs a 2-window scenario (2 `Graphics` instances sharing one `Registry`/`GlyphAtlas`) and confirms each window independently assigns and writes its own bindless slot for the atlas, with no dependency on which window ran first.

### Step C3: Revive the deleted fast CPU glyph pipeline (commit `1bd4b3593^`)

### Step C5: `jam::LowLevelGraphicsGlyphRenderer` — CPU fallback LLGC

**Scope:** New type (namespace bare `jam::`, ARCHITECT-confirmed, physically located in `jam_vulkan` module).
**Action:** Subclasses `juce::LowLevelGraphicsSoftwareRenderer`, constructed with an owned `juce::Image` render target — every virtual except `drawGlyphs` inherited unchanged (full working `fillRect`/`drawImage`/`clipToPath`/etc. via JUCE's own software rasterization). Overrides `drawGlyphs(Span<const uint16_t>, Span<const Point<float>>, const AffineTransform&)` to route through the shared `GlyphAtlas` (Step C1/C3's revived pipeline): `getOrRasterize()` per glyph into the atlas's CPU-side `juce::Image`, then a direct CPU-side SIMD blend (revived `blendMonoTinted4`/`blendSrcOver4`, Step C3) from the atlas region onto this renderer's own target image — no JUCE glyph rasterization, no GPU/Vulkan involved.
**Presentation (new, required — flagged as the primary technical risk, see Risks):** since returning non-null from `externalContextFactory` means JUCE performs zero presentation, this type presents its own rendered `Image` at frame-end via native OS calls: macOS — obtain the live `NSGraphicsContext`'s `CGContextRef` (valid since we're still inside the synchronous native paint callback when the factory runs) and `CGContextDrawImage`; Windows — `GetDC(hwnd)` (via `peer.getNativeHandle()`) + `StretchDIBits`/`BitBlt` + `ReleaseDC`.
**Validation:** Auditor confirms glyph rendering visually matches the Vulkan path's output (same atlas, same rasterization); confirms no regression to non-glyph drawing (inherited software-renderer behavior untouched). Manual ARCHITECT verification required for the native-presentation code specifically (see Risks) — this is new, unproven-in-this-codebase platform code, not something Auditor's static review alone can certify.

**BLESSED Alignment (Phase C specifics):**
- **E (Encapsulation):** `GlyphAtlas`'s CPU-only surface stays Vulkan-API-free even after relocating into the `jam_vulkan` module folder — module colocation is a build/dependency detail, not a namespace/conceptual merger (ARCHITECT-confirmed: neither `GlyphAtlas` nor `LowLevelGraphicsGlyphRenderer` are "Vulkan concepts").
- **S (SSOT):** One `GlyphAtlas`, one rasterization/packing/LRU/shaping implementation, consumed by both the Vulkan and CPU rendering paths — no parallel/competing glyph pipeline.

**Risks / Open Questions:**
- **Native presentation (Step C5) is genuinely novel in this codebase** — no existing precedent here for presenting a `juce::Image` to screen outside JUCE's own compositing.
